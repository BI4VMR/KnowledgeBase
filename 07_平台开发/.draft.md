# displayID
displayID:应用开发id，startactivity/adb shell的am start命令需要使用
物理id：截图需要指明
1. 产生机制的区别：索引 vs 硬件动态计算

    旧版本 (local:0, local:1)：
    在 Android 9 及更低版本中，系统对本地屏幕的命名非常简单粗暴。0 代表主屏（内置屏幕），1 代表副屏（如 HDMI 外接屏或折叠屏的第二块屏）。这个数字只是一个数组索引（Index），没有任何硬件绑定关系。

    新版本 (local:129 格式)：
    从 Android 10 开始，Google 重构了显示底层。这里的 129 并不是随便排的，它是一个由硬件参数计算出来的全局唯一 ID（Stable ID）。
    在底层，这个长 ID（Type-Long）通过结合 物理端口号（Port） 和 屏幕的 EDID 信息（包含制造商 ID、产品序列号等）进行位运算合成。例如，local:129 中的 129 通常代表该屏幕连接在系统的第 129 号物理端口（Port 129）上。

2. 稳定性的区别：临时工 vs 永久身份证

    旧版本 local:0：
    极其不稳定。如果设备连接了多个外接屏幕，断开再插上，或者重启系统后，原本是 local:1 的屏幕可能会因为加载顺序改变而变成 local:2。

    新版本 local:129：
    跨重启持久稳定。因为它是基于物理连接端口和屏幕硬件信息生成的，无论你重启设备多少次，或者插拔多少次，只要插在同一个物理接口上，这块屏幕在系统里的名字永远叫 local:129。

# compose 水平pager滑动偶发无效

看日志系统的touch传递是正常的，原因在于pager中嵌套了lazyverticlegrid，水平滑动可能包括垂直分量，此时事件被lazyverticlegrid抢夺导致pager无响应。

HorizontalPager 和 LazyVerticalGrid 的 scrollable 在首次 down 时都会以 awaitFirstDown + 只读 SuspendingPointerInputModifierNodeImpl 参与预检。
关键区别在于 Compose 的 awaitTouchSlopOrCancellation：谁先越过 touch slop 谁获权，另一方向被 cancel；且因为 compose 的 scrollable 常被包在 Modifier.verticalScroll/最有嵌套的容器里，父容器 scrollable 通过 performScroll/onPreScroll 会优先从嵌套连接报告消费，方向判断是"谁先检测到符合自身方向的位移，始终保持到手势结束"。
竞态：当手指位移在纵/横轴同时有分量（例如 dy 和 dx 都超过 slop 的那个瞬间），两个方向的 scrollable 都在争抢，先越过 slop 的那个拿到手势，另一个被永久取消——Compose 一旦锁定一个方向，整个手势期间不会切换到另一方向。所以"偶发不响应"正是 dy 略领先于 dx 的时刻：垂直 grid 抢到了手势，随后你把手指转成纯横向，但手势已锁定给垂直，pager 收不到，垂直 grid 又因 userScrollEnabled/内容不足而无可滚动 → 现象为"卡住不动"。

pager自带懒加载，此处不需要pager内部滑动，因此可以配置userScrollEnabled = false,使其不响应滑动。

LazyVerticalGrid(
        columns = GridCells.Fixed(columns),
        // 页面由 HorizontalPager 分页管理，禁用内部滚动，
        // 避免嵌套的垂直 scrollable 与水平 pager 竞争滑动手势。
        userScrollEnabled = false,
)

# Compose Window

ComposeView  在  removeView  时会 detach，此时它会销毁 Composition，以及这个窗口对应的  Recomposer  和  MonotonicFrameClock 。这些都是从该 View 所在窗口的 View 树上取到的，并缓存在根 View 上。再次  addView  时，Compose 会基于同一个  ComposeView  重新创建它们。

复用compose view时必须显式设置recomposer，否则动画等基于 MonotonicFrameClock 无法执行，pager滑动抬手后会卡住

val coroutineContext = AndroidUiDispatcher.CurrentThread
val runRecomposeScope = CoroutineScope(coroutineContext)
val recomposer = Recomposer(coroutineContext)
composeView.compositionContext = recomposer
runRecomposeScope.launch {
    recomposer.runRecomposeAndApplyChanges()
}

界面退出时需要cancel协程和recomposer，界面不可见需要暂停重组


没有必要复用。Compose 的创建开销很小，窗口里真正的状态都在  viewModel  中，重建  ComposeView  不会丢状态。复用的收益很小，却会遇到这类 attach/detach 的边界问题

# AAOS 16 其他应用回到Launcher主页，壁纸变黑片刻再恢复。

• 出现选择器时， CarResolverActivity  先占据 HOME 任务，用户点击后它再以  LAUNCH_SINGLE_TASK  转发启动 HomeActivity。Launcher 的任务是在这个时候新建的，被系统当作普通应用任务，而不是 home 任务（对应  wm_create_task ）。
• 一旦保存了默认 Launcher，系统直接把它按 HOME 任务启动，任务类型是  home 。
• 任务类型是  standard  时，WM 和 Shell 不会把它当作主页：转场按普通应用处理，壁纸随应用的打开和关闭被隐藏再显示。
• 壁纸反复隐藏再显示，会导致壁纸第二个窗口的 surface 每次销毁重建，UE 出第一帧比转场动画慢，所以每次返回都黑一会儿。

源码中只判断了phone的 ResolverActivity 类名，并为其拉起的界面设为home属性，未判断 AAOS 的 CarResolverActivity，因此AAOS中的选择器拉起后launcher为普通任务。

# Compose window size

基于窗口尺寸类的响应式布局

这是Compose官方推荐且最主流的适配策略。其核心思想是： 将屏幕尺寸（或更准确地说，是应用窗口的可用空间）归类到几个标准的“尺寸类”中，然后根据不同的尺寸类，决定使用何种布局结构。
3.1 引入Material 3窗口尺寸类库

首先，需要在 build.gradle.kts 中添加依赖：

dependencies {
    implementation("androidx.compose.material3:material3-window-size-class:1.2.0") // 请使用最新版本
}


这个库提供了 WindowSizeClass API，它通过 calculateWindowSizeClass 函数，将当前窗口的尺寸（扣除系统UI如状态栏、导航栏后的可用空间）归类为三种模式（紧凑、中等、扩展）的宽度和高度类别。

// 通常在 Activity 或 NavHost 的顶层可组合项中获取
@Composable
fun MyApp() {
    val windowSizeClass = calculateWindowSizeClass(activity = LocalContext.current as Activity)
    // windowSizeClass.widthSizeClass 可能是 Compact, Medium, Expanded
    // windowSizeClass.heightSizeClass 同理

    // 根据宽度尺寸类决定导航和内容布局
    when (windowSizeClass.widthSizeClass) {
        WindowWidthSizeClass.Compact -> { /* 手机竖屏或小折叠屏内屏：使用底部导航栏或导航抽屉 */ }
        WindowWidthSizeClass.Medium -> { /* 手机横屏、小平板或折叠屏展开：可能使用导航rail */ }
        WindowWidthSizeClass.Expanded -> { /* 平板、桌面或大折叠屏展开：使用永久性导航抽屉或更复杂的布局 */ }
    }
}


3.2 设计响应式导航模式

导航结构是响应式布局中最关键的一环。不同的尺寸类应对应不同的导航模式，以最优方式利用空间。

    紧凑宽度（Compact） ：空间宝贵。通常采用 底部导航栏（BottomNavigation） 或 模态导航抽屉（ModalNavigationDrawer） 。列表-详情模式中，列表和详情页面全屏切换。
    中等宽度（Medium） ：有了更多水平空间。可以采用 导航栏（NavigationRail） ，将其固定在左侧。列表-详情模式可以开始尝试并排显示，但详情部分可能仍以覆盖或动态展开的形式出现。
    扩展宽度（Expanded） ：拥有充足空间。适合使用 永久性导航抽屉（PermanentNavigationDrawer） 或更丰富的导航结构。列表-详情模式应稳定地并排显示，列表在左，详情在右，充分利用水平空间。 

实操心得 ：不要仅仅根据宽度尺寸类切换整个导航组件（如从 BottomNavigation 切换到 NavigationRail ）。更好的做法是设计一个统一的、可适配的导航状态模型（例如使用 sealed class 定义不同的导航类型），然后根据尺寸类来切换这个模型的状态。这样，你的导航逻辑会更清晰，也便于测试。

# AOSP 原生 SplitScreen 分屏实现分析

> 说明：本文只分析 AOSP 原生的分屏实现（`wm-shell/splitscreen` 模块），不涉及本项目定制的 `CarWMSplitController` 相关修改。
> 代码路径（本工程内）：
> - `sysui-core/wm-shell/src/main/java/com/android/wm/shell/splitscreen/`
> - `sysui-core/wm-shell/src/main/java/com/android/wm/shell/common/split/`
> - `sysui-core/wm-shell/src/main/java/com/android/wm/shell/draganddrop/`（拖拽入分屏）

---

## 1. 总体技术方案：TaskOrganizer + Root Task + Shell 层 `Transition`

AOSP 原生分屏**并没有通过 `WindowManager` 的 dock/多窗口旧接口实现**，而是基于一套 "Shell 主动编排窗口层级" 的机制：

1. **Shell**（`SystemUI` 进程中的 `wm-shell`）运行在系统进程中，通过 `ShellTaskOrganizer`
   向 `WindowManagerService (WMS)` 注册为 Task 的 Organizer，从而**拿到对 Task 的编排权**。
2. 分屏时，Shell 会主动 **创建两个 "Stage 根 Task"（`root task`）**，并把两个应用 Task
   **reparent 到这两个根 Task 之下**，让两个根 Task 各占屏幕一半。
3. 两者之间由一个 **Split divider（分割条）** 划分区域，divider 也是 Shell 自己创建维护的窗口/图层。
4. 所有尺寸、位置、reparent、windowingMode 的变更，都通过 **`WindowContainerTransaction (WCT)`**
   发给 WMS 生效；所有进入/退出/缩放动画都由 **Shell 层 `Transitions` 转场框架** 驱动。

一句话概括：
> **用一个"根 Task 容器"把两个 Task 组织进同一个分屏层级，用 WCT 描述布局变更，用 Transition 框架播放动画，用 Divider 提供交互。**

### 关键底层 API
| 组件 | 作用 |
|------|------|
| `ShellTaskOrganizer` | Shell 注册为 Task Organizer，`createRootTask()` 创建分屏根 Task，并接收 `onTaskAppeared / onTaskInfoChanged / onTaskVanished` 回调 |
| `TaskOrganizer.CreateRootTaskRequest` | 指定根 Task 的窗口模式（`WINDOWING_MODE_MULTI_WINDOW`）、Display |
| `WindowContainerTransaction (WCT)` | 一次原子性的层级/布局/属性变更集合（reparent、reorder、setBounds、setWindowingMode、startTask、sendPendingIntent 等） |
| `SyncTransactionQueue` | 把 WCT 按序提交/同步 Surface 事务，保证层级变更与 Surface 状态一致 |
| `Transitions` | Shell 统一转场框架；`TransitionHandler` 处理进入/退出/缩放的动画请求，`TransitionInfo` 描述每层动画 |
| `SurfaceControl.Transaction` | 真正提交图层位置/裁剪/透明度的 Surface 事务 |

## 2. 核心类及各自职责

### 2.1 `SplitScreenController.java`（分屏门面 / 对外 Controller）
- 实现对外接口 `SplitScreen`，同时实现了 `SplitDragPolicy.Starter`、`KeyguardChangeListener`。
- 职责：
  - 生命周期初始化（`onInit()`）：注册 dump、keyguard 监听、对外 AIDL `ISplitScreen` 接口、创建 `StageCoordinator`。
  - 暴露"进入/退出/启动到分屏"的高层 API：`enterSplitScreen` / `exitSplitScreen` / `startTasks` /
    `startTask` / `startIntent` / `startShortcut` / `startIntents` / `moveToStage` / `goToFullscreenFromSplit` 等。
  - 转发给内部的 `StageCoordinator`。
  - 内部类 `SplitScreenImpl`（同进程内调用）与 `ISplitScreenImpl`（跨进程，AIDL `Binder` 桩）负责对外代理。

### 2.2 `StageCoordinator`（分屏状态编排核心，最重要）
实现 `StageCoordinatorAbstract`，同时实现 `Transitions.TransitionHandler / TransitionObserver`、
`SplitLayout.SplitLayoutHandler`、`ShellTaskOrganizer.TaskListener`、`StageTaskListener.StageListenerCallbacks` 等接口。
职责：
- **管理两个 `StageTaskListener`（Main/ 侧 Stage）**，以及 `SplitLayout`、`SplitWindow` 等；
- **进入分屏**：`prepareEnterSplitScreen` → `activateSplit` → `startEnterTransition`；
- **退出分屏**：`dismissSplit` / `dismissSplitScreen` → `prepareExitSplitScreen` → `deactivateSplit` → `startDismissTransition`；
- **转场处理**：作为 `Transitions.TransitionHandler` 处理进入/退出/缩放的转场申请与动画；作为
  `SplitLayoutHandler` 处理拖动分割线时 ` 的 `onLayoutSizeChanging / onLayoutSizeChanged`；
- **拖拽/手势交互入口**：`onSnappedToDismiss`（拖拽到屏幕边缘退出并保留一侧）、`onDoubleTappedDivider`（双击换向）。

### 2.3 `StageCoordinatorAbstract`
- 抽象基类，定义分屏操作 / 属性查询 / 转场 / 事件的全部抽象方法。
- 静态工厂 `createStageCoordinator()` 根据 `enable2x1Split()` 返回 `StageCoordinator` 或 `StageCoordinator2`。

### 2.4 `StageTaskListener`（单个分屏槽（Stage）的管理）
- 实现 `ShellTaskOrganizer.TaskListener`，持有一个 `mRootTaskInfo` + `mRootLeash`（根 Task 及其 Surface）。
- 职责：
  - 构造时调用 `taskOrganizer.createRootTask(...)` 创建带 `WINDOWING_MODE_MULTI_WINDOW` 的根 Task；
  - 收集放进来/删掉的子 Task（`mChildren*`）；
  - 提供 `addTask / removeAllTasks / evictChild / reparentTopTask / activate / deactivate` 等
    **层级操作原语（只填充 WCT，真正的 hierarchy 变更由 StageCoordinator 汇总后统一提交）**；
  - 维护 dim layer、split decor、圆角裁剪等 Surface 效果。

### 2.5 `SplitLayout` + `DividerSnapAlgorithm` + `DividerView`（分屏布局 & 分割线交互）
- `SplitLayout`：计算两个 Stage 的边界（bounds）、divider 位置，负责拖动/快照动画过程中的
  **布局计算与 Surface/层级同步**；实现 `SplitLayoutHandler` 回调给 `StageCoordinator`；
  - 关键动作：`flingDividerToDismiss`（拖到边缘退出）、`snapToTarget`（吸附到比例位）、
    `setDivideRatio`、`update`、`applyTaskChanges` / `applySurfaceChanges`。
- `DividerSnapAlgorithm`：根据屏幕尺寸/inset/模式计算允许的 **SnapTarget（吸附点/退出点）**，
  例如 50/50、16:9、10/90、边缘 dismiss 等，以及 `findSnapTarget` / `getDismissEndTarget`。
- `DividerView`：分割线的触摸 UI，处理拖拽手势（`onTouch` -> `startedDragging -> mSplitLayout.fling（拖动/吸附/退出）`；
- `SplitWindowManager`：把 divider 展示为一个 overlay 窗口 `（DividerView）`，并 commit 布局状态。

### 2.6 `SplitScreenTransitions`（分屏转场动画）
- 负责启动并执行进入/退出/缩放三类转场动画：
  - `startEnterTransition` / `startDismissTransition` / `startResizeTransition`；
- `TransitSession`（含 `EnterSession` / `DismissSession`）记录每个转场的状态、remote handler、撤销回调；
- `playAnimation`：对每个 `TransitionInfo.Change` 施加位置/裁剪/alpha；支持 `RemoteTransition`（如 Launcher/桌面动画）。

### 2.7 `SplitScreen.java`（对外接口定义）
- 定义 `SplitScreen` 接口（进入/退出/启动 API + 监听器）与 `StageType` 常量
  （`STAGE_TYPE_MAIN / SIDE / A / B / C`）。

### 2.8 `ISplitScreen.aidl`（跨进程 AIDL 边界）
- 把 `SplitScreen` 的能力暴露给其它进程（Launcher / Recents / 系统 UI 等），
  远程调用会路由回 `ISystemSplitScreenImpl` → `SplitScreenController`。

### 2.9 其他辅助类
- `StageOrderOperator`：flexible split 下管理多个 Stage 的顺序/激活。
- `SplitMultiDisplay`：多显示器分屏辅助。
- `SplitscreenEventLogger`：分屏进入/退出/缩放事件统计日志。
- `SplitStatusBarHider`：分屏时状态栏显示控制。
- `SplitTransitionModifier`：根据转场信息决定是否把某任务移入/移出 Stage。

## 3. 典型调用流程

### 3.1 进入分屏（如：从 Overview 将两个应用同时拖起、拖拽应用入边、启动应用对）

**典型路径（`startTasks` 双任务进入）**

```
Launcher/Recents
  └─ ISplitScreen.startTasks(taskId1, options1, taskId2, options2, position, snap, ...)
       (AIDL 跨进程)
       └─ SplitScreenController.startTasks()                 # SplitScreenController.java
            └─ mStageCoordinator.startTasks(taskId1, taskId2, ...)  # StageCoordinator.java
                 │   └─ setStagePosition(position)            # 决定 main/side 槽位
                 │   └─ prepareTasksForSplitScreen(taskIds)   # 清空子 Task 的 bounds/windowing，让它继承根 Task
                 │   └─ 对 task1 打 ActivityOptions（setLaunchRootTask 指向 stage 根）
                 │   └─ wct.startTask(taskId1)  +  startWithTask(wct, taskId2,...)（一起打包成一个 WCT）
                 ├─ activateSplit(wct, false)                 # 让 main/side 两个 stage 都 active
                 │     └─ mStageCoordinator.activate() / mSideStage.activate()
                 └─ mSplitTransitions.startEnterTransition(TRANSIT_TO_FRONT, wct,...)
                      └─ Transitions.startTransition() -> 注册为 pending enter
                           └─ (WMShell 回调) StageCoordinator.handleRequest()/startAnimation()
                                └─ finishEnterSplitScreen(finishT)   # 布置 divider、dim、decor
```

**若是"把一个已存在 Task 移进对侧"**（如拖拽图标到屏幕另一侧，`moveToStage`）：
```
SplitDragPolicy.onDrop()  →  starter.startTask(...)  →  SplitScreenController.startTask
        └─ moveToStage(task, position, wct)          # StageCoordinator.java
             └─ mTask.addTask(task, wct)  （把该 Task reparent 到对应 Stage 根下）
             └─ activateSplit / prepareSplitLayout
             └─ startEnterTransition(TRANSIT_SPLIT_SCREEN_OPEN_TO_SIDE 或 PAIR_OPEN)
```

**关键细节**：
- 两个 Task 通过 `addActivityOptions(..., Stage)` 中 `options.setLaunchRootTask(stage.mRootTaskInfo.token)`
  指定启动时落到哪个根 Task 下（`StageCoordinator.java` 中 `addActivityOptions`）。
- `prepareTasksForSplitScreen` 会把子 Task 的 `windowingMode` 设为 `UNDEFINED`、`bounds` 置空，
  让其**自动继承根 Task 的 bounds 与多窗窗口模式**。

### 3.2 拖拽使单侧全屏（拖分割线到边缘，退出分屏但保留这一侧）

```
用户按住 divider 拖到（另一侧）屏幕边缘
  └─ DividerView.onTouchEvent -> startedDragging       # DividerView.java
       └─ onLayoutSizeChanging()/onLayoutSizeChanged()  # StageCoordinator.onLayout...()
            ├─ updateSurfaceBounds()                    # 实时把两个侧位 Surface 跟随手指
            └─ 当拖动靠近边缘：
                SplitLayout.findSnapTarget(pos, velocity, hardDismiss)  # 得到 dismiss target
                └─ mDividerSnapAlgorithm 返回 SNAP_TO_DISMISS target
                    (手指放掉后由 fling 惯性决定) 
                        └─ flingDividerToDismiss(toEnd, EXIT_REASON_DRAG_DIVIDER)  # SplitLayout.java
                             └─ 动画结束后回调 flingFinishedCallback
                                  └─ mSplitLayoutHandler.onSnappedToDismiss(toEnd,...)  # StageCoordinator.onSnappedToDismiss
                                       ├─ 计算要保留到全屏的 Stage（main or side）
                                       ├─ prepareExitSplitScreen(dismissTop, wct, EXIT_REASON_DRAG_DIVIDER)
                                       │     ├─ mSideStage.removeAllTasks / 把要去顶的 rebase bounds
                                       │     └─ deactivateSplit(wct, stageToTop)
                                       └─ mSplitTransitions.startDismissTransition(...RESON_DRAG_DIVIDER)
                                            └─ 触发 dismiss 动画，被保留的一侧放大到全屏
```

**形成的效果**：拖动分割线到边缘 → 被保留的 Stage 动画放大为全屏，另一侧被退出（其子 Task 移动到底层 / 进入 recents）。

### 3.3 退出分屏（返回全屏 / 结束分屏）

**路径 A：系统主动退出（如用户 Home、程序退出、锁屏、请求全屏）**
```
外部 -> SplitController.exitSplitScreen(toTopTaskId, EXIT_REASON_XXX)
        └─ StageCoordinator.dismissSplit()          # 或 dismissSplitScreen / dismissSplitInBackground
             ├─ clearSplitPairedInRecents(reason)   # 提示 Recents 打破该分屏配对
             ├─ prepareExitSplitScreen(stageToTop, wct, reason)
             │     ├─ 选择保留的 Stage：
             │     │    - 若指定某 stage -> 该 stage 移除其他侧 tasks, deactivate
             │     │    - 否则（双删除）全部清除
             │     └─ deactivateSplit(wct, stageToTop)    # 取消 main/side 激活，子 Task 被 reparent 出去
             └─ mSplitTransitions.startDismissTransition(wct, this, ...)
                  → 由 startAnimation() 走 dismiss 分支：展示或淡出被关闭侧，保留侧放大全屏
```

**路径 B：拖拽分割线退出（同 3.2 的 `onSnappedToDismiss`）** —— 常见为 `dragDivider`。

**路径 C：返回"单 Task 全屏"（从分屏中把某个 Task 变全屏，保留它，另一侧退出）**
```
SplitController.goToFullscreenFromSplit() 或 SystemUI 触发
        └─ StageCoordinator.goToFullscreenFromSplit()
             └─ mSplitLayout.flingDividerToDismiss(toEnd, EXIT_REASON_FULLSCREEN_SHORTCUT)
                  └─ ... 同 3.2，保留当前焦点侧到全屏
```

## 4. 关键协同点总结

| 关注点 | 承担者 | 说明 |
|--------|--------|------|
| 窗口层级组织 | `ShellTaskOrganizer` + `StageCoordinator` 创建两个 `StageTaskListener` root task | 两个应用被 reparent 到两个 root 之下 |
| 布局/大小计算 | `SplitLayout` + `SplitDecorManager` | 计算左右上下的 bounds，divider 位置 |
| 吸附/退出判定 | `DividerSnapAlgorithm` | 生成各 SnapTarget，判定 dismiss Window |
| 交互（拖 divider） | `DividerView` | 触摸事件驱动 realtime window 缩放 |
| 动画 | `SplitScreenTransitions` + `Transitions` | 进入/退出/缩放三流程，可自定义 `RemoteTransition` |
| 对外接口 | `SplitScreen` + `ISwitchScreen.aidl` | 同进程 `SplitScreenImpl` + 跨进程 `ISplitScreenImpl` |

---

## 5. 一句话小结

AOSP 分屏的本质是：
> **由 wm-shell 通过 ShellTaskOrganizer 创建两个多窗口分屏根 Task，把两个应用 Task 组织进这两个 Stage，
> 用 WindowContainerTransaction 一次性下发布局与 reparent 变更，用 Transitions 框架做进入/退出/缩放动画，
> 由 DividerView + SplitLayout + DividerSnapAlgorithm 提供拖拽、吸附、边缘退出的交互逻辑。**

进入 = "创建 Stage 根 + 把应用放进来 + 启动进入转场"；
拖拽到边缘 = "实时改 bounds + 到边缘判定 dismiss + 保留一侧并放大 + 启动退出转场"；
退出 = "把另一侧 Task 移出 Stage 根（reparent 回 Display/TaskDisplayArea）+ 取消 Stage 激活 + 启动退出转场"。
