# displayID
displayID:应用开发id，startactivity/adb shell的am start命令需要使用
物理id：截图需要指明
1. 产生机制的区别：索引 vs 硬件动态计算

    旧版本 (local:0, local:1)：
    在 Android 9 及更低版本中，系统对本地屏幕的命名非常简单粗暴。0 代表主屏（内置屏幕），1 代表副屏（如 HDMI 外接屏或折叠屏的第二块屏）。这个数字只是一个数组索引（Index），没有任何硬件绑定关系。

    新版本 (local:129 格式)：
    从 Android 10 开始，Google 重构了显示底层。这里的 129 并不是随便排的，它是一个由硬件参数计算出来的全局唯一 ID（Stable ID）。
    在底层，这个长 ID（Type-Long）通过结合 物理端口号（Port） 和 屏幕的 EDID 信息（包含制造商 ID、产品序列号等）进行位运算合成。例如，local:129 中的 129 通常代表该屏幕连接在系统的第 129 号物理端口（Port 129）上。

2. 稳定性的区别：临时工 vs 永久身份证

    旧版本 local:0：
    极其不稳定。如果设备连接了多个外接屏幕，断开再插上，或者重启系统后，原本是 local:1 的屏幕可能会因为加载顺序改变而变成 local:2。

    新版本 local:129：
    跨重启持久稳定。因为它是基于物理连接端口和屏幕硬件信息生成的，无论你重启设备多少次，或者插拔多少次，只要插在同一个物理接口上，这块屏幕在系统里的名字永远叫 local:129。

官方文档已确认，来自 Android Gradle Plugin 的  CommonExtension.buildToolsVersion  API 参考页：

未指定  buildToolsVersion  时，AGP 会自动使用"该插件版本所要求的最低 Build Tools 版本"（minimum version of the build tools required by the version of the plugin you're using）。

具体到你的情况：

• AGP  9.3.1  要求的默认/最低 Build Tools 版本是  36.0.0 （这与之前编译报错  Failed to find Build Tools revision 36.0.0  完全吻合，证实了默认值确实跟随 AGP 版本，而不是跟随  compileSdk ）。
• 这个默认值不是"最新已发布版本"，而是"该 AGP 版本硬编码要求的最低版本"，所以即使你本地只装了更新的  36.1.0 ，AGP 也不会自动接受，必须精确匹配或显式声明。

官方文档来源：

1.  CommonExtension.buildToolsVersion  API 参考（属性文档原文引用如上） 
https://developer.android.com/reference/tools/gradle-api/9.0/com/android/build/api/dsl/CommonExtension#buildToolsVersion()
3. Build Tools 发布说明（各版本 Build Tools 变更记录）
4. AGP 9.3.0 发行说明也明确了该版本对应的 Build Tools 兼容矩阵

补充说明： 该属性也可以在  settings.gradle.kts  的  SettingsExtension.buildToolsVersion  中统一设置一次，对所有子项目生效，比在每个模块里重复声明更简洁——如果你希望我帮你把之前加到 9 个模块里的  buildToolsVersion = "36.1.0"  收敛到  settings.gradle.kts  里统一配置，我可以现在处理。

搜索了整个代码库，确认： PORT_NUMBER  这个  resValue  在代码里完全没有被引用（没有  R.string.PORT_NUMBER ，没有 XML 里的  @string/PORT_NUMBER ，也没有  getString(...)  调用它）。

 resValue  和  BuildConfig  是两套完全不同的机制：

CarLauncherStatsLog.java

libs

模块编译分为jacac产物和kotlin产物，二者有重叠的部分与不重叠的部分，使用时需要将重叠的部分合并，防止重复类错误，重新打包即可

turping - 包含java和kt的接口，但没有实现，仅适用于compileonly场景，通常为framework.jar android.car.jar,或某些厂商定制的内置模块。

turping - combine 包含java和kt的接口，以及依赖项，不能用于应用开发，因为应用自己会通过gradle引入依赖，加上这些jar内置的依赖会冲突。
