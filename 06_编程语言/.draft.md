isolation

隔离级别 - 等同于数据库ACID级别。

传播行为

是指多个业务方法都包括事务时，如何进行调度。

REQUIRE 没有事务则新建，已有事务则加入 （默认）

surrpots 没有事务则非事务执行，已有事务则加入

mandatory 必须在事务中运行，调用者没有开启事务则抛出异常

REQUIRE_new 挂起旧事务，在新事务中执行。挂起表示新旧事务无关，新事务回滚不影响旧的事务。

not_support 不在事务中运行，如果调用者线程有事务则将其挂起。

never 不准使用事务，调用者开启事务则抛出异常

nested 开启嵌套事务，新事务可以独立回滚，不影响外层事务；如果调用者没有事务则新建一个事务。

# ffmpeg

要理解这一点，我们需要看看这两 waste 机制在底层是如何运作的：
1. FF_THREAD_FRAME (帧级多线程)

    工作原理： 它通过同时解码多个连续的帧来提高速度。例如，线程 1 解码第 1 帧，线程 2 解码第 2 帧。

    代价： 这种机制必然带来输入到输出的延迟（Latency）。因为要喂饱和管理多个线程，解码器通常需要缓存一定数量的帧（通常等于线程数）才能开始输出第一帧。

2. AV_CODEC_FLAG_LOW_DELAY (低延迟)

    工作原理： 强制解码器立刻输出当前解码的帧，绝对不进行内部缓存。它要求解码器满足“输入一帧，立刻输出一帧”的实时性要求，常见于实时视频通话或直播。

    代价： 无法利用需要跨帧缓存的优化算法，且无法进行帧级并行。

线程模式兼容 LOW_DELAY 吗？延迟表现适用场景FF_THREAD_FRAME❌ 不兼容较高（延迟 $N$ 帧）本地文件播放、视频转码（追求高吞吐量）FF_THREAD_SLICE兼容极低（0 帧延迟）实时连麦、低延迟直播（追求极致低延迟）

# Scrcpy 二次开发
## 简介
scrcpy包含服务端与客户端两个部分，服务端运行在 Android设备上，负责屏幕与音频捕获、编码，并注入客户端发送的触控事件。客户端运行在 PC 端，负责解码服务端发送的数据包，显示画面并播放音频。

我们可以利用scrcpy的服务端实现，开发定制化的客户端，实现远程控制或自动化测试。


## 工作流程

PC            Android

1. -> 推送服务端文件

将服务端文件传递到设备的可写入目录，通常为 /data/local/tmp/scrcpy-server

adb push ./jar /data/local/tmp/scrcpy-server

2. -> 开启转发通道

在设备上创建 Unix domain socket端点，将其映射到pc端口，以便客户端与服务端建立连接。

adb forward tcp:$localPort", "localabstract:scrcpy_00012222


localabstract是android的本地套接字，与Unix domain socket类似，在android sdk中对应的类名为LocalSocket


reverse 下 PC 先监听，server 启动后主动连，连上就说明 server 正常。forward 下 adb 的端口在 PC 本地一直是通的，即使设备端 server 还没起来，PC 的  connect  也会成功（adb 先接受，再往后转发），所以无法判断 server 是否真在监听。

forward 需要 dummy byte。 为了弥补上面的问题，forward 模式下 server 在  accept()  后先写 1 字节 0（ sendDummyByte ），PC 读到它才确认连接真的通了。reverse 不需要。（ server.c  约 498 行的注释就是在说这个。）



3. 开启服务端

adb shell
CLASSPATH=/data/local/tmp/scrcpy-server app_process / com.genymobile.scrcpy.Server 4.1 tunnel_forward=true scid=00012222

4.1是版本号，服务端将在启动阶段校验其文件内置版本号是否和用户输入的值相同，防止运行过程中协议不匹配出现不可预期的错误。

tunnel_forward=true 表示当前为 forward模式，false表示reverse模式，应当与前一步中选择的转发方式匹配。

SCID 是一个 8 位字符串，用于区分同时启动的多个服务端，此处将端口号作为 SCID。

这些是必备选项，其他选项详见源码的 server/<...>/Options.java

常用选项

"display_id=${displayID}",
"video_codec=${videoCodec.cli}",
"video_bit_rate=$bitRate",
"max_fps=$maxFPS",
"max_size=$maxSize",
"audio=$enableAudio",
"audio_codec=${audioCodec.cli}"
"audio_bit_rate=$audioBitRate"
"control=true",
"log_level=verbose"

4. 建立连接

客户端按照视频、音频、控制通道的顺序，与服务端建立TCP连接。

以上通道根据配置可能会发生变化

只禁用视频时 第一通道为音频，第二通道为控制，无第三个通道
只禁用音频时 第一通道为视频，第二通道为控制

以此类推。

## 2. 入口 `Server.main`（`…/scrcpy/Server.java`）

1. `main()`：捕获所有异常，`finally` 里 `System.exit(status)`（避免 Android SDK 的非守护线程阻止退出）。
2. `internalMain()`：
   - 设置默认 `UncaughtExceptionHandler`（记录日志）。
   - `dropRootPrivileges()`：若 uid==0，`android.system.Os.setuid(2000)`（切到 shell 用户，否则剪贴板失效，issue #6224）。
   - `prepareMainLooper()`：`Looper.prepare()` 后**反射**写入 `Looper.sMainLooper`，使其允许 quit（普通 `prepareMainLooper` 不允许）。
   - `Options.parse(args)`（`…/scrcpy/Options.java`）：解析 `key=value` 参数，第一个参数为版本号，不一致则抛异常。
   - `Ln.disableSystemStreams()` / `Ln.initLogLevel()`（`util/Ln.java`），打印设备信息（`Build.MANUFACTURER/BRAND/MODEL`、`Build.VERSION.RELEASE`）。
   - 若是 `list_*` 请求（编码器/显示器/相机/应用列表）：`LogUtils.build*ListMessage()` 输出后直接返回，不镜像。
   - 否则调用 `scrcpy(options)`。

## 3. `Server.scrcpy(options)` 主流程

### 3.1 版本校验
使用 `Build.VERSION.SDK_INT` 与 `AndroidVersions` 检查：相机需 Android 12+，新虚拟显示 / IME policy 需 Android 10+，否则抛 `ConfigurationException`。

### 3.2 `CleanUp.start`（`…/scrcpy/CleanUp.java`，可选）
- 启动 `cleanup` 线程，通过 `ProcessBuilder` / `Command.exec` **再拉起一个** `app_process … CleanUp` 子进程。
- 主 Server 被 kill 时（如 USB 拔出），子进程负责恢复：`settings` 中的 show_touches、stay_on_while_plugged_in、屏幕关闭状态、显示器电源模式、禁用 IME policy 等，并删除设备上的 jar。

### 3.3 `Workarounds.apply()`（`…/scrcpy/Workarounds.java`）
由于没有真实 App 环境，全部靠反射：
| 操作 | API |
|---|---|
| 构造 `ActivityThread` 并写 `sCurrentActivityThread`、`mSystemThread` | `android.app.ActivityThread`（`getDeclaredConstructor` / `Field.set`） |
| 构造 `AppBindData`，设置 `appInfo.packageName = com.android.shell`，写 `mBoundApplication` | `ActivityThread$AppBindData` |
| `Instrumentation.newApplication(Application.class, FakeContext.get())` → 写 `mInitialApplication` | `android.app.Instrumentation`、`FakeContext`（`…/scrcpy/FakeContext.java`，包名 `com.android.shell`） |
| Android 14+ 补 `ConfigurationController` | `android.app.ConfigurationController` |
| `getSystemContext` | `ActivityThread.getSystemContext()` |
| 修复 `AudioRecord`（Android 11 上无法正常 Builder.build） | `AudioRecord` 私有构造器 `AudioRecord(long)`、字段 `mRecordingState` |

### 3.4 `DesktopConnection.open`（`…/scrcpy/device/DesktopConnection.java`）
- **reverse 模式**（默认）：`new LocalSocket().connect(new LocalSocketAddress("scrcpy_<scid>"))` 依次连 video → audio → control（按启用情况）。
- **forward 模式**：`new LocalServerSocket(name)` + `accept()`，并先 `write(0)` 发一个 dummy byte 让客户端确认连接。
- 随后 `sendDeviceMeta(Device.getDeviceName())`：写入 64 字节设备名（`Build.MODEL`）。
- 获得各 socket 的 `FileDescriptor`（`LocalSocket.getFileDescriptor()`）交给 `Streamer` 直接写。

### 3.5 创建 AsyncProcessor
`AsyncProcessor`（接口：`start(TerminationListener)` / `stop()` / `join()`）有三类实现：

| 组件 | 类 |
|---|---|
| 控制 | `control/Controller` |
| 音频 | `audio/AudioDirectCapture` 或 `AudioPlaybackCapture` + `AudioRawRecorder` 或 `AudioEncoder` |
| 视频 | `video/ScreenCapture` / `NewDisplayCapture` / `CameraCapture` + `SurfaceEncoder` |

`Streamer`（`device/Streamer.java`）负责编码数据包的封装：stream header（codec id、宽高）+ 每包 12 字节 frame header（PTS + flags：`PACKET_FLAG_CONFIG/KEY_FRAME`）+ 数据。

### 3.6 启动与等待
- `Completion(running)`：每个 processor 结束时 `addCompleted(fatalError)`；全部结束或发生致命错误则 `Looper.getMainLooper().quitSafely()`。
- 逐个 `asyncProcessor.start(...)`，主线程 `Looper.loop()` 阻塞。
- `finally`：`cleanUp.interrupt()` → 各 `stop()` → `connection.shutdown()` → `join()` → `OpenGLRunner.shutdown()` → `connection.close()`。

## 4. 视频线程（`SurfaceEncoder` + `SurfaceCapture`）

`SurfaceEncoder.start()` 新建线程 → `streamCapture()` 循环：

1. `capture.init()` / `capture.prepare()`；`MediaCodec.createByCodecName(encoderName)` 或 `createEncoderByType(mime)`（H264/H265/AV1）。
2. `MediaFormat` 配置：码率、`KEY_COLOR_FORMAT = COLOR_FormatSurface`、帧率、I 帧间隔、`repeat-previous-frame-after` 等。
3. `mediaCodec.configure(..., CONFIGURE_FLAG_ENCODE)` → `createInputSurface()` → `capture.start(surface)` → `mediaCodec.start()`。
4. `streamer.writeVideoHeader()`；循环 `dequeueOutputBuffer(bufferInfo, -1)` → `streamer.writePacket(...)` → `releaseOutputBuffer`。
5. 屏幕尺寸/旋转变化（`CaptureControl` + `DisplayMonitor` 回调）时发送 EOS，重新配置编码器。若编码器失败且开启 `downsizeOnError`，缩小分辨率重试（`VideoConstraints` / `prepareRetry`）。

# 认证方案


加密：攻击者可能看到消息，但无法理解内容。

认证：确认对方不是攻击者。



预共享密钥

A 生成密钥，使用者通过邮件 IM软件等已有的加密通道发送给 B ，B使用该密钥进行认证。

不能直接使用 A 与 B 之间的通道，如果通道未加密可能被中间人捕获，如果通道有加密中间人可以伪造身份截获消息，双方无法验证对方的身份。



P2P 应用

IP随时会变，无法通过CA提前签发证书

方案 1：
TOFU（Trust On First Use，首次使用信任原则）—— 最契合P2P原理：类似于 SSH 连接第一次连接远程服务器时的机制。客户端在第一次与节点建立连接时，获取并本地缓存该节点的自签证书公钥或指纹（Fingerprint）。在后续的连接中，只要对方出示的证书指纹与第一次保存的一致，就信任该连接。优点：完美适配没有域名、IP 经常变动、无法使用公共 CA 的 P2P 场景。缺点：如果初次连接时遭受中间人攻击（主动攻击），恶意公钥会被错误信任。因此，初次交换指纹时，通常需要结合带外验证（例如：通过安全的二维码扫描、已登录的中心化信令服务器转发、或者文本口令比对）。

方案 2：内置私有根证书（Private CA / Root CA Pinning）   原理：开发者在自己的应用生态内部构建一个私有的根证书颁发机构（Root CA）。用这个私有根 CA 动态签发各个 P2P 节点的叶子证书。   实现方式：将该私有根证书的公钥直接硬编码（Hardcode）或打包在你的 P2P 客户端软件中。优点：应用内的所有节点互相通信时，只要是由这个私有根签发的证书，客户端都会无条件信任。无需每次都做 TOFU 确认。   缺点：如果私有根证书的私钥泄露，整个 P2P 网络将面临全局安全风险。

方案 3：基于预共享密钥的 TLS / DTLS-PSK (Pre-Shared Key)   原理：如果 P2P 节点双方在连接前可以通过某种方式（如中心化信令服务器、账号登录凭证）安全地共享一个密钥（PSK），那么可以完全抛弃复杂的证书体系，直接使用 TLS-PSK 或 DTLS-PSK（数据报传输层安全）。   优点：无需生成、分发和验证复杂的 X.509 证书，握手开销极小，非常适合资源受限或需要快速建立连接的 P2P/IoT 场景。

方案 4：利用去中心化身份（DID）或公钥指纹作为标识原理：在一些现代 P2P 网络（如 WebRTC 的底层、IPFS、Matrix）中，节点的“身份”本身就是其公钥的哈希（PeerID）。实现方式：通信时双方直接交换各自的公钥，并用该公钥对会话进行签名验证（自证明身份，Self-Certifying ID）。TLS 层的证书可以直接动态生成，只要验证“证书中的公钥哈希 == 对方的 PeerID”，就可以直接建立加密且可信的连接。

证书摘要对比

用于首次连接时，验证对方身份，识别是否存在中间人攻击。


正常情况下

A  <-> B

A | B
B | A

二者一致，因此身份正确。


A -> 中间人 <- B


中间人如果给A发B的公钥，给B发A的公钥，可以使得两端显示一致，但由于没有双方的私钥，此时无法解密消息。
为了截获数据，中间人发送自己的公钥摘要

A | C
B | C

二者大概率不一致，A与B核对时能够发现问题

采用证书计算完整摘要时，攻击者很难找到使得两侧显示摘要相等的证书，因此可以认为几乎无法破解。




Numeric Comparison（数字对比）

在客户端显示完整的摘要结果，用户可能会觉得麻烦从而直接点击确认，安全机制失效，因此可以将摘要取部分数据，显示为4-8位的短码，便于用户对比。

采用证书计算短码时，值域空间为 10 ^ 6，攻击者可以使用很多证书进行匹配，寻找使得两端数字相同的第三个证书，从而监听所有数据，因此通常还需要引入以下机制。



Nonce（Number used once）随机数

只进行摘要对比，容易穷举

无法防止重放攻击

攻击者虽然不知道这个加密密文（Ciphertext）里写的究竟是什么（因为他没有密钥解密），但他通过观察流量特征，知道这个密文在特定场景下代表“执行某个关键动作”。

如果没有随机数，某一次合法配对的所有交互数据（公钥、计算出的配对码、确认信号）如果被恶意攻击者录制下来。

在未来的某个时间，如果设备因为某种原因重置了信任关系，或者攻击者试图欺骗用户重新走一次配对流程，攻击者就可以用这些旧的录像去“重放”整个欺骗过程，诱导用户在毫无防备的情况下再次按下“确认信任”。


Commitment Scheme

随机数作为配对码生成依据后，仍可能被穷举，使攻击者构造出在两端相同的数据包。使得双向显示号码相同的伪消息。

双方先交换随机数和公钥的hash
再交换公钥和随机数

客户端发送数据前，hash已提前发送到服务端 ，攻击者难以反推原随机数并构造出符合hash的假数据，进行篡改。提高中间人攻击的难度。


# TLS
SSL -> TLS

验证服务端身份，交换临时密钥，并进行加密通信。


mTLS 双向加密，普通tls适用于大多数浏览器应用，验证服务端身份，避免客户端访问虚假网站，

双向加密适用于定制化系统和P2P应用，需要验证双方身份，防止客户端伪造身份。



# JKS

JKS（Java KeyStore） 存储公钥、私钥、证书



常见 SSL 证书格式

    .der .cer: 二进制文件，只保存证书，不保存私钥。
    .pem：可保存证书，可保存私钥。
    .crt：不保存私钥。
    .pfx .p12: 二进制文件，同时包含证书和私钥，一般有密码保护。
    .jks: 二进制文件，同时包含证书和私钥，一般有密码保护
